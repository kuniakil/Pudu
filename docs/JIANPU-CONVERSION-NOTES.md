## 2. 两种「简谱」的体裁（重要区分）

对比语料后发现，数字谱领域至少有三种不同体裁，**混在一起谈会导致需求错位**：

### 2.1 伴奏谱 / 弹唱谱（`如願.jpg`）

```
Bm⁷  E⁷  Amaj⁷  Dmaj⁷  Bm⁷  G♯m⁷(♭5)  C♯⁷  F♯m      ← 和弦标记（谱上方）
4   3̲4̲3̲  2̲ 1̲ 2̲ 2̲ 7̲  3̲-  0  1̲ 3̲ ...            ← 数字 + 节奏线
你 是 遥 远 的 路，  山 野 大 雾 里 的 灯，             ← 歌词
```
- **有和弦标记**（绝对和弦名：Bm7 / E7 / Amaj7 / Dmaj7 / G#m7(b5) / C#7 …）
- 有装饰音（`\1` `1\`）、连音弧、附点、三连音（`34` 括线）、八度点
- 左手/伴奏声部用**数字**表示，但和弦语义由上方的和弦标记承担

### 2.2 演唱谱 / 成品简谱（`如願 好聽版`、`月下煮茶`）

- **没有和弦标记**
- 数字 + 节奏线 + 歌词（`如願`）或纯数字（`月下煮茶`，器乐）
- 声部用**大谱表括号 `{}`** 分上下两行（伴奏声部也是数字）
- 行首小节号 `(1)` `(5)`
- 灰度区分：灰色数字 = 弱奏/延留音，非灰色 = 正拍

> **结论**：目标体裁（2.2）**不需要和弦标记**。这直接绕开了 §4 描述的最难问题。

## 4. 固定调 vs 首调，以及真正难的地方

### 4.1 固定调 → 首调（相对简单）

五线谱用固定调（absolute pitch），简谱用首调（movable-do）。

- 简谱数字 = 该音在调内主音上的级数
- 判定不难：给定调号 + 音高，级数是查表运算
- 调外音（临时升降）→ 简谱里用 `#` `b` 标注在数字旁
- **注意首调体系下，移调后数字不变、和弦名要重算** —— 若有和弦标记层，移调必须同时重算该层

### 4.2 真正的难点：左手伴奏 → 和弦标记

用户（做过类似程序）的判断：**五线谱把和弦完整写出来，简谱的伴奏部分却用和弦标记（和弦记谱）表示。要转换，程序必须先理解那是什么调、那块的音构成什么和弦，才能用和弦方式记谱。**

这个判断是对的，而且可以拆得更细。难点有五层：

**(a) 不是同时性问题，而是「型态」问题**
真实钢琴伴奏的左手常常是**分解和弦 / 琶音型**（`如願.jpg` 的 `Bm7` 底下是 `5̲ 2̲ 4̲ 1̲ 3̲ 5̲` 这样的流动音型），
而不是同时奏响的一叠音。**「哪些音同时響」推不出和弦**，必须先做型態分析。

**(b) 和弦符号是「約簡」，不是音集合的精確描述**
`Bm7` = B D F♯ A，但實際演奏可能是：根音在低音、可能省略五音、可能加九音、可能轉位。
符號本身帶有編曲者的取捨。

**(c) 延伸音 / 變和弦是編輯決定，不是推導結果**
`Amaj7` / `A` / `Aadd9` / `A6` 在音樂內容上可能**完全相同**（甚至 A maj7 的七音根本沒出現）。
`G♯m7(♭5)`（半減七和弦）更是特定風格選擇。**從音符內容無法唯一決定和弦質性與延伸音。**

**(d) 和弦變化點也是編輯決定**
多久換一次標記？每個變化和弦都標？還是只標「重要」的？這是人的判斷。

**(e) 需要調性語境**
同一個音塊在不同調裡是不同和弦；簡譜的絕對和弦名（如 `F♯m`）vs 傳統簡譜理論的功能級數（`Ⅵ級`）
是兩套標法；移調時兩者都要跟著變。

### 4.3 關鍵區分：**有 MusicXML 就沒有 (a)(b)(c)(d) 的難度**

| 輸入 | 和弦資訊 | 難度 |
|---|---|---|
| MusicXML 檔（MuseScore / Sibelius / Finale 匯出） | **已經在 `<harmony>` 元素裡** | **零難度**，直接讀出即可 |
| 五线谱**圖片**（掃描/拍照） | **不存在**，必須從音符推導 | §4.2 的全部難度 |

> 這是本筆記最重要的一句話。**「五线谱 → 简谱」之所以難，是因為起點是圖片。**
> 一旦有 MusicXML，和弦、速度、標題、歌詞（`<lyric>`）全是結構化欄位，不必推導。

## 5. 歌詞：另一道牆

- Audiveris（OMR 引擎）只認五線譜上的**音符、調號、拍號**，**不做中文歌詞 OCR**
- 五線譜圖檔裡的歌詞是印在五線譜下方的文字，要認出來並對位到音符：
  需要「中文 OCR + 音符時間軸對齊」——字元數與音符數不 1:1（拖腔、裝飾音、一字多音、一音多字）
- MusicXML 裡歌詞是 `<lyric>` 結構化欄位 → 有 MusicXML 就零難度

**歌詞是 OMR 這條路最硬的一道牆。**

## 6. 素材型態的關鍵事實（本次評估的實測發現）

`如願.jpg` / `如願01.jpg` / `如願02.jpg` **不是五線譜，是數字譜**（數字 + 節奏線 + 歌詞 + 和弦）。
→ **Audiveris 對這類檔案完全無效**（它只認五條線與音符符號）。

因此實務上要分三種輸入處理：

| 輸入型態 | 需要的引擎 | 歌詞 | 和弦 |
|---|---|---|---|
| 五線譜圖片 | Audiveris OMR | 需另建中文 OCR（極難） | 需推導（極難） |
| 數字譜圖片 | 需自建數字譜 OCR | 需中文 OCR（較易，文字較規整） | 可直接讀（已在圖上） |
| MusicXML | 直接讀 | 讀 `<lyric>` | 讀 `<harmony>` |

## 7. 可行的替代路線（依推薦序）

### 路線 A：先驗證現成服務（零開發）
目標語料出自 **eopiano.cn**，該站本身有上傳轉換功能。
**先確認它能不能直接吃五線譜圖檔、輸出 §2.2 那種格式。** 能 → 問題結束。
這是成本最低、資訊量最高的一步：能立刻驗證「這件事本身可不可行」。

### 路線 B：換渲染引擎（保留 OMR 前段）
Pudu 的 L2 渲染器整個替換成專業簡譜渲染器：

- **JianpuRender**（npm `jianpurender`，TS/SVG，開源免費）
  支援：歌詞對位、小節號、速度標記、SVG/PNG 匯出
  未見支援：多聲部、和弦標記
  https://github.com/flufy3d/JianpuRender
- **MuseScore 4 Jianpu plugin**（桌面端，排版最接近專業成品，含歌詞）
  https://musescore.org/en/project/jianpu-numbered-notation
- ~~OSMD Jianpu mode~~ → **sponsor 付費版**，排除

解掉「排版像網頁」這一半，**解不了歌詞**（除非來源已有 MusicXML）。

### 路線 C：繞開 OMR，改走 MusicXML
五線譜圖檔 →（人工或半自動）MuseScore 開檔 → 存 MusicXML → 簡譜渲染器。
辨識誤差直接歸零（沒有識別這一步）；歌詞/和弦/標題/速度全部結構化可得。
代價：每份譜要人工開一次檔。

### 路線 D：自建（工作量 ×10 以上）
只有當路線 A/B/C 全部證偽、且確實需要全自動時才考慮。
順序：數字譜 OCR → 數字譜解析（節奏線/八度點/裝飾音）→ 和弦標記推導 → 中文歌詞 OCR + 對位 → 專業排版引擎。
