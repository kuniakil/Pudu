## 2. 三种「简谱」体裁（重要区分，混谈会导致需求错位）

### 2.1 伴奏谱 / 弹唱谱（`如願.jpg`）——**含和弦标记**

```
Bm⁷  E⁷  Amaj⁷  Dmaj⁷  Bm⁷  G♯m⁷(♭5)  C♯⁷  F♯m      ← 和弦标记（谱上方）
4   3̲4̲3̲  2̲ 1̲ 2̲ 2̲ 7̲  3̲-  0  1̲ 3̲ ...            ← 数字 + 节奏线
你 是 遥 远 的 路，  山 野 大 雾 里 的 灯，             ← 歌词
```
左手/伴奏声部用**数字**表示，但和弦语义由上方的和弦标记承担。

### 2.2 双手简谱（`如願 好聽版`、`月下煮茶`）——**不含和弦标记** ⭐

- **没有和弦标记**（已逐页核对 3 页全部确认）
- 数字 + 节奏线 + 歌词（`如願`）或纯数字（`月下煮茶`，器乐）
- 声部用**大谱表括号 `{}`** 分上下两行（伴奏声部也是数字）
- 行首小节号 `(1)` `(5)`
- **灰色数字** = 延留/弱奏（跨小节延音的音、倚音等）
- 特征记号：三连音（`32` 加括线）、竖向波浪线（颤音/琶音）、倚音、附点、八度点、连音弧

> **用户的参考文件属于这一类。**

### 2.3 一般简谱（右手数字 + 左手只给和弦符号）

用户描述的、**他之前做过的程序**的产物形态：左手不写出来，只标一个和弦符号。

### 2.4 ⭐ 关键判断：目标体裁决定要不要碰最难的问题

| | 左手怎么写 | 需要和弦识别吗？ |
|---|---|---|
| 2.2 双手简谱（**本项目目标**） | 左右手都是数字 | **不需要** —— 左手和右手是同一个操作（固定音→首调级数） |
| 2.3 一般简谱 | 只写和弦符号 | **需要** —— §4.2 的全部难度 |

**所以「五线谱 → 双手简谱」这条路上，用户认为最难的那个问题（左手→和弦识别）并不在路径上。**

## 4. 固定调 vs 首调，以及真正难的地方

### 4.1 固定调 → 首调（相对简单）

五线谱用固定调（absolute pitch），简谱用首调（movable-do）。

- 简谱数字 = 该音在调内主音上的级数
- 判定不难：给定调号 + 音高，级数是查表运算
- 调外音（临时升降）→ 简谱里用 `#` `b` 标注在数字旁
- **注意首调体系下，移调后数字不变、和弦名要重算** —— 若有和弦标记层，移调必须同时重算该层

### 4.2 真正的难点：左手伴奏 → 和弦标记（**仅 2.3 体裁需要**）

用户（做过类似程序）的判断：**五线谱把和弦完整写出来，简谱的伴奏部分却用和弦标记表示。
要转换，程序必须先理解那是什么调、那块的音构成什么和弦，才能用和弦方式记谱。**

这个判断是对的，拆开是五层：

**(a) 不是同时性问题，而是「型态」问题**
真实钢琴伴奏的左手常常是**分解和弦 / 琶音型**（`如願.jpg` 的 `Bm7` 底下是 `5̲ 2̲ 4̲ 1̲ 3̲ 5̲` 这样的流动音型），
而不是同时奏响的一叠音。**「哪些音同时響」推不出和弦**，必须先做型态分析。
→ 左键柱式和弦（同时响）：音集合直接给出 → 根音/性质/转位可解
→ 左键琶音型：音散在时间上 → 必须先切分时间单元，难度高

**(b) 和弦符号是「约简」，不是音集合的精确描述**
`Bm7` = B D F♯ A，但实际演奏可能是：根音在低音、可能省略五音、可能加九音、可能转位。
符号本身带有编曲者的取舍。

**(c) 延伸音 / 变和弦是编辑决定，不是推导结果**
`Amaj7` / `A` / `Aadd9` / `A6` 在音乐内容上可能**完全相同**（maj7 的七音根本没出现）。
`G♯m7(♭5)`（半减）是特定风格选择。**从音符内容无法唯一决定和弦性质与延伸音。**

**(d) 和弦变化点也是编辑决定**
多久换一次标记？每个变化和弦都标？还是只标「重要」的？这是人的判断。

**(e) 需要调性语境**
同一音块在不同调里是不同和弦；简谱的绝对和弦名（如 `F♯m`）vs 传统简谱理论的功能级数（`Ⅵ级`）
是两套标法；移调时两者都要跟着变。

### 4.3 ⭐ 关键区分：**有 MusicXML 就没有 (a)~(d) 的难度**

| 输入 | 和弦信息 | 难度 |
|---|---|---|
| MusicXML 文件（MuseScore / Sibelius / Finale 导出） | **已经在 `<harmony>` 元素里** | **零难度**，直接读出即可 |
| 五线谱**图片**（扫描/拍照） | **不存在**，必须从音符推导 | §4.2 的全部难度 |

> **「五线谱 → 简谱」之所以难，是因为起点是图片。**
> 一旦有 MusicXML，和弦、速度、标题、歌词（`<lyric>`）全是结构化字段，不必推导。

### 4.4 用户给的调性/拼写例子（已拆解，可解）

《月下煮茶》原曲 B 调：

```
五线谱：5 个升号  →  调号 = B 大调（或 G# 小调，靠终止音/首音判别）
简谱：1=B                                    ← 首调的主音 = B
一级和弦：写「1」（级数记法）或写「B」（绝对记法）  ← 两种并存
二级小和弦：级数记法写「2m」
            → 绝对记法：B 大调的第 2 级 = C# → C# 小 = #Cm
```

**拼写（`#C` 还是 `D♭`）完全由调号决定**：5 个升号 → 用升号拼；5 个降号 → 用降号拼
（Db 大调的第 2 级 = E♭ → `E♭m`）。

所以「必须先理解那是什麼调」＝ **调号 → 主音 → 拼写规则**，这条链是查表可解的，不神秘。

**真正会咬人的是转调**：曲中转调后首调的参照点要重设，`1` 的意义跟着变 —— 这才是有难度的部分。

## 5. 歌词：另一道墙

- Audiveris（OMR 引擎）只认五线谱上的**音符、调号、拍号**，**不做中文歌词 OCR**
- 五线谱图片里的歌词是印在五线谱下方的文字，要认出来并对位到音符：
  需要「中文 OCR + 音符时间轴对齐」——字数与音符数不 1:1（拖腔、装饰音、一字多音、一音多字）
- MusicXML 里歌词是 `<lyric>` 结构化字段 → 有 MusicXML 就零难度

**歌词是 OMR 这条路最硬的一道墙。** 但注意：《月下煮茶》**没有歌词**（器乐），
所以验证「五线谱 → 双手简谱」这条路时，歌词不是阻塞项。

## 6. 素材型态的关键事实（实测发现）

`如願.jpg` / `如願01.jpg` / `如願02.jpg` **不是五线谱，是数字谱**（数字 + 节奏线 + 歌词 + 和弦）。
→ **Audiveris 对这类文件完全无效**（它只认五条线与音符符号）。

| 输入型态 | 需要的引擎 | 歌词 | 和弦 |
|---|---|---|---|
| 五线谱图片 | Audiveris OMR | 需另建中文 OCR（极难） | 需推导（极难，仅 2.3 体裁） |
| 数字谱图片 | 需自建数字谱 OCR | 需中文 OCR（较易） | 可直接读（已在图上） |
| MusicXML | 直接读 | 读 `<lyric>` | 读 `<harmony>` |

## 7. 可行的路线

### 路线 A：先验证现成服务（零开发）⭐ 优先
**已经有现成服务在做这件事**，可能根本不用自己开发：
- **[gangqinpu.com](https://www.gangqinpu.com/)**（虫虫钢琴）—— 五线谱/简谱切换，有「转简谱」功能
- **[8pu.cn](https://8pu.cn/)** —— 在线制谱，支持简谱/功能简谱/和弦谱/五线谱，**AI 识别转谱**，
  多谱式混排对照
- **[miaogaichong.com](https://miaogaichong.com/)**（反谱）—— AI 音乐转谱，输出 MusicXML/MIDI
- **everyonepiano.cn** —— 同页提供五线谱 + 简谱（本身就是「转简谱」服务）

**先确认这些服务能不能直接吃五线谱图片、输出 §2.2 那种格式。** 能 → 问题结束。

### 路线 B：换渲染引擎（保留 OMR 前段）
Pudu 的 L2 渲染器整个替换成专业简谱渲染器：

- **JianpuRender**（npm `jianpurender`，TS/SVG，开源免费）
  支援：歌词对位、小节号、速度标记、SVG/PNG 汇出
  未见支援：多声部、和弦标记
  https://github.com/flufy3d/JianpuRender
- **MuseScore 4 Jianpu plugin**（桌面端，排版最接近专业成品，含歌词）
  https://musescore.org/en/project/jianpu-numbered-notation
- ~~OSMD Jianpu mode~~ → **sponsor 付费版**，排除

解掉「排版像网页」这一半，**解不了歌词**（除非来源已有 MusicXML）。

### 路线 C：绕开 OMR，改走 MusicXML
五线谱图片 →（人工或半自动）MuseScore 开档 → 存 MusicXML → 简谱渲染器。
辨识误差直接归零（没有识别这一步）；歌词/和弦/标题/速度全部结构化可得。
代价：每份谱要人工开一次档。
《月下煮茶》在 musescore.com 上有现成的 Piano Solo 谱，可直接取 MusicXML。

### 路线 D：Fork 已有项目 ⭐ 用户倾向
用户打算**寻找并 fork 别人已经解决「五线谱→简谱」算法的仓库**，而不是从零自建。
理由：算法部分若已有成熟解，fork 改造比从零做快很多。

**待办：调研现存的「五线谱 → 简谱」开源项目**，评估其算法覆盖度、许可证、维护活跃度。
候选方向：MusicXML→简谱的转换器（JianpuRender / lzh9102/musicxml_to_jianpu / jianpu-ly）、
OSMD 的 jianpu 分支、以及中文圈可能的「简谱 OCR/生成」项目。

### 路线 E：自建（工作量 ×10 以上）
只有当路线 A~D 全部证伪、且确需全自动时才考虑。
顺序：数字谱 OCR → 数字谱解析（节奏线/八度点/装饰音）→ 和弦标记推导 → 中文歌词 OCR + 对位 → 专业排版引擎。
